# 数据库设计 —— 功能分析（score_db）

数据库脚本：`schema.sql`（在 DataGrip / Navicat / mysql 命令行整段执行）
归属：林嘉辉（数据库相关）

---

## 一、数据库总体信息

| 项目 | 设计 |
|---|---|
| 数据库名 | `score_db` |
| 字符集 / 排序规则 | `utf8mb4` / `utf8mb4_general_ci`（支持中文、emoji） |
| 存储引擎 | `InnoDB`（支持事务、外键、行级锁） |
| 数据表 | `student`（学生）、`course`（课程）、`score`（成绩）、`user`（用户） |

脚本开头先 `DROP DATABASE IF EXISTS` 再 `CREATE DATABASE`，保证可重复执行。

## 二、四张表的结构

### 1. student 学生信息表
| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INT | 主键、自增 | 代理主键 |
| student_id | VARCHAR(20) | 非空、唯一 | 学号（业务键） |
| name | VARCHAR(50) | 非空 | 姓名 |
| class_name | VARCHAR(50) | 非空 | 班级 |
| gender | CHAR(2) | 默认'男' | 性别 |
| age | INT | 默认 18 | 年龄 |

### 2. course 课程信息表
| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INT | 主键、自增 | 代理主键 |
| course_id | VARCHAR(20) | 非空、唯一 | 课程号 |
| course_name | VARCHAR(100) | 非空 | 课程名 |
| credit | FLOAT | 非空、默认 2.0 | 学分 |
| semester | VARCHAR(20) | 非空 | 开课学期 |

### 3. score 成绩表（核心关系表）
| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INT | 主键、自增 | 代理主键 |
| student_id | VARCHAR(20) | 非空、外键→student | 学号 |
| course_id | VARCHAR(20) | 非空、外键→course | 课程号 |
| score | FLOAT | 非空、CHECK 0~100 | 成绩 |
| semester | VARCHAR(20) | 可空 | 学期 |

约束：
- 外键 `fk_score_stu`：student_id 引用 student(student_id)；
- 外键 `fk_score_cou`：course_id 引用 course(course_id)；
- **联合唯一** `uk_stu_course(student_id, course_id)`：同一学生同一课程只能有一条成绩；
- **检查约束** `ck_score_range`：成绩必须在 0~100。

### 4. user 用户表
| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INT | 主键、自增 | 代理主键 |
| username | VARCHAR(50) | 非空、唯一 | 登录名 |
| password | VARCHAR(255) | 非空 | djb2 哈希密码（非明文） |
| role | ENUM('admin','teacher','student') | 非空 | 角色 |
| student_id | VARCHAR(20) | 可空 | 学生角色关联学号 |

## 三、表之间的关系（E-R）

```
student 1 ───────< N score N >─────── 1 course
   （一个学生有多条成绩；一条成绩属于一个学生、一门课程）
user(student角色) ── student_id 逻辑关联 ──> student
```

- `student` 与 `course` 是**多对多**关系，通过 `score` 这张连接表拆解为两个一对多。
- `score` 同时是"选课关系表"和"成绩实体表"。
- 成绩表用外键保证：不能给不存在的学生/课程录入成绩。

## 四、用到的约束与设计要点

1. **主键**：每张表用自增 `id` 作代理主键，业务号（学号/课程号）另加唯一约束，
   主键稳定、不受业务变化影响。
2. **外键约束**：保证数据引用完整性（referential integrity）。
3. **唯一约束**：学号、课程号、用户名唯一；成绩表用联合唯一防止重复录入。
4. **检查约束 CHECK**：把成绩范围限制在数据库层。
5. **非空 / 默认值 / 枚举**：进一步保证数据合法性。
6. **密码哈希存储**：`123456` 的 djb2 哈希为 `000006527dd1705a`，不存明文。
7. **符合三大范式**：
   - 1NF：每个字段原子不可再分；
   - 2NF：非主属性完全依赖主键；
   - 3NF：非主属性不传递依赖（如班级、课程名没有冗余存进成绩表，需要时 JOIN 取出）。
8. 主键和唯一键会自动建立索引，提升按学号/课程号查询的效率。

## 六、答辩可能被问到的问题

**Q1：为什么用 utf8mb4 而不是 utf8？**
A：MySQL 的 utf8 最多 3 字节，无法存储部分 4 字节字符（如某些 emoji、生僻字），
utf8mb4 才是完整的 UTF-8。

**Q2：为什么用 InnoDB？**
A：InnoDB 支持事务、外键和行级锁，本系统需要外键保证数据完整性，且并发性能更好。

**Q3：学生和课程是什么关系？怎么实现？**
A：多对多——一个学生选多门课，一门课有多个学生。用 score 连接表拆成两个一对多，
并在 score 上加两个外键。

**Q4：怎么防止同一学生同一课程重复录入？**
A：对 (student_id, course_id) 建联合唯一约束，插入重复数据时数据库会拒绝。

**Q5：为什么同时有自增 id 和学号？**
A：自增 id 是稳定的代理主键，内部关联和索引高效；学号是业务键，可能因教务规则变化，
用唯一约束保证不重复即可，不直接拿它做外键的被引用列更稳妥。

**Q6：删除学生/课程为什么有时失败？**
A：score 表有外键引用它们，只要还有成绩记录，为防止产生"孤儿数据"，数据库会拒绝删除。

**Q7：满足第几范式？**
A：满足第三范式，字段原子、无部分依赖、无传递依赖，成绩表只存学号和课程号，
姓名、班级、课程名通过 JOIN 获取，避免冗余和更新异常。
